# 備份、升級與復原

[English](../backup-and-recovery.md) | **繁體中文**

至少在應用程式資料目錄之外保留一份加密副本，並在 NAS 之外的另一個故障範圍保留副本。請依資料需求選擇保留週期，並定期在獨立儲存空間測試復原。從未實際還原的備份，不能作為充分保障。

## 兩種不同的備份

| 類型                      | 包含內容                                                           | 登入憑證與工作階段                                 | 適用情境                               |
| ------------------------- | ------------------------------------------------------------------ | -------------------------------------------------- | -------------------------------------- |
| 包含圖示檔案的可攜式 JSON | 服務、分類、標籤、外觀與經驗證的圖示內容                           | 不包含；保留目的端管理員／工作階段／稽核／速率限制 | 組態復原，以及遷移至新管理員           |
| 停機後的完整資料封存檔    | SQLite 資料庫、任何 WAL／共用記憶體檔案、圖示資源與鎖定 inode 內容 | 包含密碼／工作階段摘要、稽核與速率限制狀態         | 使用相容軟體與擁有權，精確復原整個安裝 |

兩種備份都不包含 Compose 環境、反向代理設定或 TLS 私密金鑰。請另行保護這些資料，並記錄經審查的映像／原始碼版本。備份含有私人網址與名稱，不應附加到公開 issue。應用程式不會替匯出檔或封存檔加密。

## 可攜式匯出與還原

1. 登入並開啟「管理 → 備份」（Manage → Backup）。
2. 保持啟用「包含圖示檔案」（Include icon files）後匯出。只有中繼資料的匯出，若仍參照被省略的圖示，便不可還原。
3. 保護下載的 UTF-8 JSON，並複製至應用程式／NAS 儲存空間以外。
4. 測試復原時，以獨立儲存空間建立新執行個體，完成受保護的新管理員設定並登入。
5. 選擇 JSON、驗證、檢查數量與設定變更警告，確認取代後提交一次。
6. 驗證服務連結、我的最愛／順序、分類／標籤、外觀、可見性／私人模式與圖示顯示。啟動器只開啟主要連結；匯出 LAN／WAN 替代連結不會啟用自動切換。

驗證／預覽不會取代資料。權杖綁定工作階段，有效期五分鐘，而且提交嘗試即會消耗權杖，即使提交失敗也一樣。重試前請重新驗證。成功還原會保留經驗證、全域唯一的 UUIDv4 ID 與排序位置，更新時間戳記／修訂版本，並保留目的端管理員、工作階段、稽核與速率限制。既有設定草稿之後可能衝突，必須明確重新載入。

完整可還原組態的上限為 **16 MiB，包含圖示 base64 的精確展開大小**。所有接受的實體／圖示變更都會在交易中強制檢查，超限回傳 `409 LIMIT_EXCEEDED`，不會部分寫入。其他上限為服務／分類／標籤各 5000 筆、圖示 1024 個、每個圖示 1 MiB，以及 0 至 2147483647 的排序位置。請勿任意修改內容來掩蓋驗證失敗，或重新序列化損壞輸入以隱藏重複 JSON 鍵。不支援的備份版本、不安全內容或缺失的參照圖示，必須從可信任來源修正後再匯入。

還原外觀可能改變公開／私人模式與可見性。對訪客開放前，請檢查警告並驗證實際暴露內容。私人模式不等於備份加密。

## 停機後建立完整 Docker 封存檔

**請勿只複製使用中的 `nexa.db`，或漏掉使用中的 WAL 檔案。** 程式執行時使用可攜式匯出；否則先停止應用程式，再複製完整資料目錄。請勿刪除鎖定檔：停止程序會釋放核心鎖，而不移除 inode。

以下範例使用標準專案與本機環境檔，請從原始碼工作目錄的根目錄執行。`c` 只是便利的 shell 函式，不是應用程式命令：

```sh
set -eu
c() { docker compose --env-file deploy/.env -f deploy/compose.yaml "$@"; }
umask 077
backup_dir=$(mktemp -d "$HOME/nexa-backup.XXXXXXXX")
c stop nexa-home
container=$(c ps --all --quiet nexa-home)
test -n "$container"
docker cp --archive "${container}:/data/." - > "$backup_dir/data.tar"
(cd "$backup_dir" && sha256sum data.tar > data.tar.sha256)
c up --detach --no-build --pull never --wait
printf 'Private backup directory: %s\n' "$backup_dir"
```

封存串流保留數字形式的擁有權與私有權限，不會將憑證資料解壓縮至公開主機目錄。目錄維持 `0700`、檔案維持 `0600`；主機外的副本應加密，並盡可能另存校驗碼。校驗碼可偵測損壞，但無法抵擋能同時替換兩個檔案的攻擊者，因此不等於真實性保護。

任何命令失敗都會中止此流程；來源服務可能刻意保持停止。請檢查錯誤，再決定何時重啟。請勿在同一資料目錄初始化另一個服務，也不要使用全域 prune 排解問題。

原生執行時，請先正常停止程序，再由目錄擁有者封存**整個**私有資料目錄，保留數字擁有權與權限。若要在原生與 Docker 擁有權之間遷移，優先使用可攜式 JSON。完整封存檔會保留原始 UID；請勿以允許所有人寫入來解決不相符問題。

## 將封存檔復原至獨立儲存空間

不要在唯一的正式環境副本上實驗。保留來源資料卷與封存檔，不要變更。使用備份所記錄、精確相容的映像／原始碼版本；較舊執行檔遇到未知的新版結構會拒絕啟動，而不是降級它。

1. 在可信任備份所在目錄驗證校驗碼：

   ```sh
   cd /absolute/private/backup-directory
   sha256sum -c data.tar.sha256
   ```

2. 回到原始碼工作目錄。將環境檔複製為已被 Git 忽略的 `deploy/.env.recovery`，並修改為隔離復原設定：回送位址綁定、未使用的連接埠（例如 `18081`）、精確的 `http://127.0.0.1:18081` Origin、無可信任代理，以及明確的本機 HTTP Cookie 例外。不要對網際網路開放。選擇相容且已在本機建置的映像。

3. 選擇從未使用過的新專案名稱，並確認沒有同名專案的容器或資料卷。所有復原命令都應使用該名稱：

   ```sh
   set -eu
   recovery_project="nexa-recovery-$(date -u +%Y%m%d%H%M%S)-$$"
   existing_containers=$(docker ps -aq --filter "label=com.docker.compose.project=$recovery_project")
   existing_volumes=$(docker volume ls -q --filter "label=com.docker.compose.project=$recovery_project")
   test -z "$existing_containers"
   test -z "$existing_volumes"
   r() { docker compose --project-name "$recovery_project" --env-file deploy/.env.recovery -f deploy/compose.yaml "$@"; }
   r create --no-build --pull never nexa-home
   target=$(r ps --all --quiet nexa-home)
   test -n "$target"
   ```

4. 只還原至這個全新、已停止的容器／資料卷。將 `backup_dir` 設為已驗證的私有備份絕對路徑：

   ```sh
   docker cp --archive - "${target}:/data" < "$backup_dir/data.tar"
   r run --rm --no-deps nexa-home doctor
   r up --detach --no-build --pull never --wait
   ```

5. 開啟隔離的復原 Origin，使用**封存檔中的**管理員憑證登入。完整封存檔會保留初始化與工作階段，不應產生新設定權杖。請驗證所有圖示、服務目錄／順序／可見性／設定、新的可攜式匯出及正常變更操作。Doctor 會檢查已知結構版本、SQLite 完整性、外鍵與儲存圖示位元組；不會重設登入憑證，也不會清理孤立檔案。

6. 切換為正式環境前，先停止復原與正式執行個體，恢復正式 HTTPS／Origin／Cookie 設定。可再次完整複製已停止的資料至新的正式資料卷，或明確將正式掛載切換到已驗證的復原資料卷。保留舊資料卷。請勿讓暫存與正式應用程式同時使用相同資料。將選定的掛載／專案對應保存在受保護的部署設定。

切換掛載的覆寫設定可將已驗證的復原資料卷標示為 **external**，使正式 Compose 不擁有或刪除它：

```yaml
services:
  nexa-home:
    volumes:
      - recovered_data:/data
volumes:
  recovered_data:
    external: true
    name: REPLACE_WITH_THE_VERIFIED_RECOVERY_VOLUME_NAME
```

本機覆寫檔應放在已被 Git 忽略的 `.local/`，後續 Compose 命令必須一致包含它。正式環境使用此外部資料卷期間，必須保留復原專案與資料卷。保留期間不要對任何一個專案執行 `down --volumes`。獨立備份與新正式執行個體驗證完成後，清理也必須由維運者針對精確已知資源另行明確決定，不可使用查詢結果進行批次刪除。

## 升級流程

1. 閱讀版本說明及支援架構／結構變更，固定使用經審查的原始碼修訂或已驗證映像，不要使用未審查的浮動映像。
2. 匯出包含圖示的完整可攜式 JSON，建立停機後的完整封存檔，並記錄精確的舊映像／原始碼與部署設定。
3. 在本機建置目標版本，或取得另行驗證的發行產物。保留資料卷、專案名稱、Origin、代理信任與私有擁有權。本機建置與分支／PR 檢查不會發布映像；版本 tag 發布方式請見[發行指南](releases.md)。
4. 使用保留的資料卷啟動一個目標執行個體。啟動時會以資料鎖序列化遷移、檢查已知結構，並在向前遷移前建立安全快照。此類資料卷內快照不能取代卷外備份及其相符圖示資源。
5. 檢查就緒狀態、版本、受限日誌、登入、公開／私人行為、圖示與新匯出。確認正常停止／啟動可保留資料與預期工作階段。
6. 新版本驗收前保留舊備份／映像。不要只因健康檢查成功就丟棄復原依據。

回復舊版時，先停止目標版本。較舊執行檔只能搭配它支援的結構版本。若結構已升級，請以相容的舊映像，將**升級前的完整備份**復原至獨立儲存空間、驗證後，再於兩個執行個體皆停止時切換掛載。請勿強制變更 `user_version`、修改初始遷移，或只覆寫資料庫而留下不相符的圖示資源。

## 登入憑證遺失與資安事件復原

系統沒有預設密碼、電子郵件重設或未經驗證的重設端點。管理員密碼遺失時，請保留舊安裝，建立新的私有資料目錄／資料卷、完成受保護設定，再匯入最新的**可攜式**備份。此流程刻意使用新管理員來復原組態。停機完整封存檔則會還原舊帳戶／密碼摘要；複製它不會重設未知密碼。沒有可用的可攜式備份時，不提供支援的自動登入憑證重設流程；請保留資料並尋求可信任維護者的離線協助，不要刪除資料表或資料。

若懷疑遭入侵，請隔離存取、保留停機後的鑑識副本與受保護日誌，再使用乾淨主機／映像及可信任備份。變更管理員密碼以撤銷所有工作階段，並在重新開放前檢查服務網址、可見性、圖示與代理設定。基礎設施副本可能還原舊工作階段摘要，因此事件復原後變更密碼很重要。若私人網址暴露了其他 NAS／服務憑證，也應在 Nexa Home 之外輪替這些憑證。

損壞或不安全的目錄應拒絕通過檢查。請保護封存檔與日誌，只在離線時執行 doctor，並將已知正常的副本復原至新儲存空間。不要以 `chmod 777` 掩蓋損壞、停用檔案鎖、修改結構版本、略過 TLS 驗證，或刪除唯一備份。
